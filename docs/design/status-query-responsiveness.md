# 状态查询响应与历史推导复用

状态：2026-11-10 已实施并完成离线、原生 CPU 闭环、保留运行只读比较和安装验证。
全量检查与修复后的定向复验分别保留，不宣称单次全量全绿。

## 失败与实施边界

2026-11-10 的只读观察中，Unix socket 连接、发送均不足 0.2 ms，
STATUS 等待分别为 9.229 s、43.547 s；紧接着同版本请求仅用 0.015 s。
离线状态投影约 0.061 s，140 KiB 响应的编码约 0.001 s。
这证明调度与控制请求共用主线程的排队问题，不能把全部等待归因于某个函数。
历史推导重复解析 JSON、复制大对象，监控显示阶段反复校验嵌入输入，进一步
占用 CPU。用户已停止研究任务并授权修复、验证及 dev/main 发布；已有研究根、
冻结 bundle、Profile 和资源池保持原样。

## 最小机制与来源

1. 可复现失败是慢 tick/控制操作阻塞 STATUS；增加客户端超时不能隔离它们。
2. 边界是 Host 单写线程与只读观察者。数据库和正式 reducer 仍是状态来源，
   传输线程不获得写能力，也不自行计算生命周期或费用。
3. Git、事务、主键、原子写、类型和普通测试能保护内容，却不能让同一线程在
   阻塞时应答。复用已有 STATUS 投影，只增加内存发布和有限传输队列。
4. 主线程在启动、控制操作后及 tick 间发布独立序列化副本。副本携带生成时间、
   单调时钟年龄和原 run revision；不持久化、不新增 schema 或完成标记。
   维护成本是新鲜度、容量和线程关闭测试；若 Host 将来拥有统一只读服务，
   将此传输交接并入该服务。

## 实施方案

- 一个非阻塞 socket 线程处理原 control.sock。STATUS 直接读取发布副本；
  其他请求进入有限队列，仍由主线程调用现有 handle/事务逻辑。
  半帧和不读响应的客户端有总时间限制；队列满明确拒绝；断开不取消已排队命令。
  关闭时最多用一秒排空已完成的回复，避免命令已提交却丢失应答；未处理的请求
  不会被伪造为已接纳。空闲终态仍按发布周期刷新，避免每个 tick 重建状态。
- 保留状态副本的 run revision，增加 status_snapshot 元数据。五秒以上副本
  不再用于监控的实时富化。命令的 expected_revision 仍由正式事务检查。
- 既有 StateStore 缓存保存最终的批次、参与者控制、会合和交互推导；
  保留提交/回滚失效与返回副本隔离，不缓存时钟和资源活体判定。
- 阶段标签只解析已有 task_context 类型，不为显示阶段解码全部嵌入输入。
  Agent 接纳、执行和 Oracle 的完整校验不变。

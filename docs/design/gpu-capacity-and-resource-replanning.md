# GPU 容量反馈、资源修订与同卡共享设计

状态：2026-09-27 用户授权的 ACI 27 / bwrap65 实现完成。
后续余量讨论已纳入本次范围；G1 发现的四项问题已解决，最终 301 项聚焦回归通过。
完整范围及原始失败见 [qualification](../qualification.md#current-development--gpu-capacity-and-resource-replanning-2026-09-27)。

目标：避免资源申请在空闲授权设备上也无法满足时持续等待，并降低未知显存峰值
工作负载同卡并发引发的 OOM。设计适用于不同课题、模型、GPU 型号和设备数量。
不修改既有研究运行、已接纳 Profile、实验预注册或共享池服务；不包含上下文恢复修复。

## 1. 已复现的问题及当前能力

本地只读证据位于 `.local/analysis/research-progress-20260927-1850/`。
问题复现时的补充观察为 2026-09-27 19:09：授权 GPU 0 利用率 0%，无池承诺；实际空闲
约 24120 MiB，扣除框架保留的 4096 MiB 后可分配 20024 MiB。
待执行实验的最终工作负载预算为 20288 MiB，无法满足。

待执行实验的 Agent 原始申请实际为 16384 MiB。既有
`resolve_workload_memory_mib()` 根据本工作负载归属实测峰值 16984834048 bytes，
换算为 16198 MiB，再乘 1.25 并按 64 MiB 对齐，得到 20288 MiB。
Agent 曾取消较早的申请并降低申报值，但相同实测下界仍生效，新申请再次等待。
只告诉 Agent “空闲显存不足”或让它降低申报值无法解决此问题。

同一运行的另外两项实验曾在同卡上分别使用约 15.82 GiB 与 7.71 GiB，
造成三个 trial OOM。它们启动时另一张授权卡仍在忙，后来释放不会迁移在途进程。

现有能力应继续复用：

- `compute_resources.py`：设备观察、授权边界与显存保留保护。
- `resource_experience.py`：按同一工作负载、同一所有者的实测记录解析最终预算。
- `gpu_pool.py`：事务内准入、稳定请求身份、启动前复查、归属采样及释放。
- `shared_gpu_host.py`：资源查询、已接纳估计及实测来源、池请求协调。
- Host 与实验工具：提交、等待、取消、前置失败、终态收集及
  `replaces_experiment_id` 修订链。
- EXECUTION handoff：Agent 交还等待后，Host 在实验终态唤醒它。

当前缺口是：单一 `capacity_unavailable` 原因不区分可等与需改；资源查询不直接
解释最终准入预算；资源申请不满足时实验不终结，已 handoff 的 Agent 无法修订。

## 2. P0：同一容量判定，明确下一步

复用 `_capacity()` 的计算和实测预算解析器，给 `get_resources`、提交反馈、
`wait_experiment`、Host STATUS 与 Web/TUI 提供一致的解释。
这些是既有状态和观察的投影，不建立另一个资源事实库。

| 情况 | 判断依据 | 框架行为 |
|---|---|---|
| 当前可运行 | 当前空闲减尚未驻留的承诺足以覆盖工作负载与保留量 | 原有事务准入及启动前复查 |
| 暂时占用或公平等待 | 设备最大可用容量可以满足，但当前空闲/承诺/排队次序不允许 | Host 继续等待，不反复调用模型 |
| 当前授权容量下无法满足 | 有可靠设备容量资料，且满足需求的授权 GPU 数量少于 gpu_count | 返回明确需要修订的资源原因；进入下文修订路径 |
| 采样、归属或容量未知 | 缺少支持上述结论的信息 | 保留未知并等待/提示，不当成零占用或永久不可行 |

不得用一次低 free、0% 利用率或“无本池请求”推断设备永久空闲。其他用户进程、
驱动保留内存和短时占用必须区分。

可运行判定沿用：

```
free_memory_mib - outstanding_memory_mib
    >= resolved_workload_memory_mib + effective_reserve_memory_mib
```

结构性容量判定使用当前可靠的设备可供应用使用的容量上界，例如物理总量减去
后端可靠报告的系统/驱动保留；不能把 total-free 全部当成固定保留。
进一步扣除池配置与本请求的保留量，但不把其他运行暂时要求的更高保留量当成
永久限制。逐卡计算，再检查 gpu_count；支持异构设备，不只检查第一张卡。
后端无法可靠区分保留内存时，保留量为 unknown，使用物理总量作为保守上界；
只有需求连这个上界也无法满足时才能要求修订，不能把未知保留量猜成某个固定值。

在现有设备观察中补充可选的驱动/系统保留容量及来源；未知后端不伪造数值。
新字段只是遥测，与现有 free/total 和实际准入规则交叉核对。

`get_resources` 增加可选的既有 `resource_estimate` 输入，使用同一校验器和
预算解析函数预览结果；无参数查询保持可用。返回至少包括：

- Agent 申报值、Profile 下限/初始值、实测峰值与已有 Attempt 引用。
- Host 余量与取整后的最终工作负载预算、单独的设备保留量。
- 每张授权卡当前可分配量、已知容量上界、差额、观察时间与未知原因。
- 当前可运行、可等待或需要修订的结论。

预览不预留 GPU，不冻结后来提交的来源；实际提交仍重新验证并通过现有规则
保存当时接纳的来源。涉及外部进程的信息只展示容量汇总，不泄露其他用户身份。

## 3. P0：资源不可满足时完成技术收尾并唤醒 Agent

提交前可以确定不可满足的申请：直接返回可操作的工具拒绝，不创建无效实验或池请求。

对于已接纳但尚未启动的实验，在当前可靠容量资料下无法满足时：

1. Host 在现有命令/转换记录中先记录该实验的技术终结意图，停止对同一实验新派发。
2. 复用池 release 和已有进程注册检查，确认不存在正在启动/运行的归属进程。
   无法确认时保持现有清理/恢复流程，不提前宣称释放成功。
3. 通过既有启动前失败、合成终态及结果接纳路径完成技术失败，记录资源原因与
   计算依据；保留 synthetic_before_spawn/absence 信息，不伪造 PID、GPU 实测或执行时间。
4. handoff 等待看到真实终态后，按现有 EXECUTION 后续调用机制唤醒所属 Agent。
5. Agent 检查技术失败与实测来源，优化实际内存需求后通过原有
   `submit_experiment(replaces_experiment_id=...)` 提交修订。

不得覆盖已预注册的 resource_intent，也不得把资源失败映射为科学 REFUTED。
并发启动、取消、清理失败和 Host 崩溃均使用现有命令 ID、Attempt 身份和恢复记录
协调；同一故障只产生一次终态结果，不允许旧池请求在修订后迟到启动。

已确定需要修订的队首申请不应一直阻挡其他可运行工作：池的候选选择跳过该
不可派发项并交回 Host 收尾；普通容量等待仍保留原有公平规则，不能泛化为任意插队。

修订使用已有实验修订次数、实验数量、Agent 调用和总运行预算；耗尽后按既有
技术失败或资源决策路径处理，不自动追加预算。同一不变资源方案重复提交时，
准入返回相同具体原因，不通过新 ID 制造新的排队工作。

## 4. P1：未知峰值优先独占，可信小任务仍可共享

“优先空卡”只能解决有空闲卡的情况，不能防止两张卡都忙时继续塞入未知工作负载。
已实现的新策略如下：

- 没有完整、成功、同工作负载归属实测的实验，默认要求单卡独占池内工作负载。
- 有匹配成功实测的实验，在最终预算、现有承诺和设备保留量均满足时允许同卡共享。
- 共享请求不能进入已有独占承诺的卡；该约束在池事务内双向检查，覆盖多个 Host。
- 有空闲且可满足的设备时优先分散；没有空卡时，未校准实验等待，不挤入在途实验。
- 独占仍需满足工作负载预算与保留量，不能用“独占”绕过本次 20288 > 20024 的限制。
- 无法控制的外部进程仍受实时容量和现有归属/压力保护约束，独占不宣称物理设备绝无他人使用。
- 已采样峰值是观测下界，成功实测加余量也不是未来无 OOM 的保证。

共享许可由 Host 从已接纳估计及既有 Attempt 证据推导，Agent 不直接填写。
为使不同 Host 在同一池中原子执行此规则，最小扩展是在已有 resource_intent 与
池 `intent_json` 中携带独占/共享调度属性，池沿用事务中的 active 请求进行验证。
不把其他运行的私有实测数据复制到池，也不建立第二个学习数据库。

相关最小扩展的必要性说明：

1. 具体失败：同卡未校准任务的实际峰值超过申报预算，导致另一个科研实验多 seed OOM。
2. 失败边界：Host 掌握工作负载证据，池负责跨 Host 准入；当前数字预算不能表达共享许可。
3. 现有事务/ID 能防止重复和竞态，但不能推导请求未携带的调度语义。
   只在 Host 先检查空卡再提交会被另一个 Host 的并发申请打破；普通测试不能代替运行时原子判定。
4. 最小机制：既有 intent 中一个调度属性，复用其校验、事务和归属。
   成本是协议兼容处理、策略验证和旧请求覆盖；若未来池能从同一既有可信来源直接获得
   该属性，则合并掉传输冗余。当前不添加新散列、证书、清单、校准标记或状态账本。

保留现有 Profile 的 `initial_vram_per_experiment`、硬下限和实测余量含义。
不同 batch/precision/shape 的证据不混用；改变实现后必须准确描述新工作负载并重新测量，
不得仅改标签绕过同一负载的历史峰值。设备保留策略保持不变；用户随后授权将
下面的自适应任务余量纳入本次实现，实际 OOM 后的预算增长仍保持 25%。

### 25% 余量的后续评估

25% 是修复前实现的固定保守策略，不是由本次记录验证的最优比例。按本次
16198 MiB 归属采样峰值，25% 后取整增加 4090 MiB，再叠加设备保留 4096 MiB，
比已观测峰值多留约 8 GiB。两者分别覆盖工作负载增长和设备级余量；池对同一
设备的 reserve 取最大值，不按任务数累加。Agent 申报与实测预算也取最大值，
没有再把 Agent 申报值统一乘 1.25。

| 实测余量（仅算术比较） | 工作负载预算 MiB | 加 4096 MiB 保留后 | 相对当时 free 24120 MiB 的余量 |
|---|---:|---:|---:|
| 25% | 20288 | 24384 | -264 |
| 20% | 19456 | 23552 | 568 |
| 15% | 18688 | 22784 | 1336 |
| 10% | 17856 | 21952 | 2168 |

20% 可以通过当时的容量算式，但不代表已验证能完整运行。来源 Attempt 为
FAILED，1904 次归属采样均完整、unknown 为零；这只说明已采样点的归属完整，
不证明连续峰值或全部训练/验证阶段均已覆盖。它因共享显存压力中止，不能作为
稳定成功运行的校准证据，也不能当作该工作负载独占仍必然 OOM 的证据。

本次实施采用以下可复算规则：原有 Attempt 范围及准确的 workload 匹配保持
不变；最近失败/测量未知之后的完整成功记录，其最大峰值必须覆盖更早观测峰值。
满足时采用 15%；至少三个这样的成功记录且最大峰值不超过最小值的 105% 时采用
10%；两者都有 512 MiB 绝对余量下限并向上对齐 64 MiB。不满足时保持 25% 与
初始预算，默认池内独占。启动前终结或未执行的容量丢失不作为工作负载测量来源。
共享许可由同一预算解析结果推导。现有实测引用在首次提交时接纳，后续重放不查询
新历史，也不根据某次排队差额裁剪预算。实际 OOM 仍独立放大旧预算 25%。

Oracle 继续独立核对原始 Attempt、所有权、时间和 GPU 归属，再调用同一纯预算
函数解释已验证来源；不复制一套自适应 reducer。比例和样本门槛是可测试的工程
策略，不宣称已由本次科研运行证明最优，实际 CUDA 稳定性/收益需要另行有限评估。

## 5. Agent 与用户可见行为

Web/TUI 及工具反馈显示不同原因，而不是统一“等待 GPU”：

- 等待设备释放：需求可以满足，当前被占用。
- 等待独占设备：缺少完整可比实测，暂不与在途工作共享。
- 需要调整资源方案：列出最终工作负载预算、可用容量与差额。
- GPU 信息未知：列出采样失败或容量资料缺失原因。

本次案例应能解释为：“申报 16384 MiB；实测加余量后按 20288 MiB 准入；
GPU 0 当前可分配 20024 MiB；需要修订实际内存需求，降低申报值不会改变实测下界。”

更新既有 resource-planning/experiment-repair 运行时指导：降低实际峰值、调整
批处理方式或执行安排；涉及 batch、precision 等科学配置变化时仍遵守实验协议
与原有验证，不由框架自动代改。框架不自行补跑 seed 或拼接失败实验指标。

新增一次明确状态变化通知复用已授权通知通道和现有去重机制；轮询不反复发通知。
只在确实需要变更授权 GPU、资源预算或科学条件时请求用户决策。

## 7. 兼容与范围

P0 新行为按现有运行版本机制作用于新建运行；旧 bundle、Profile、研究结果及
预注册保持原样。协议新增字段必须保留旧字段集合的读取能力；新 Host 对缺少
必要能力的旧池明确报告不兼容，不静默假定其支持独占或容量解释。
不原地替换正在服务既有运行的共享池。P1 的池部署与新运行启动单独安排。

这份方案不直接解除当前旧运行的等待；当前运行的取消、修订或重启必须作为
具体操作另行授权。本次开发验证只使用独立测试运行，代码提交不代表升级既有共享池。

## 8. 按工作负载保留显存（2026-10-05）

用户要求保留同运行 FIFO，减少固定 4096 MiB 的设备保护余量。只读实测中，
一个 Process 因空闲 4068 MiB 持续低于 4096 MiB 被保护终止，未观察到 OOM；
另一个较小请求虽有容量仍在队首大请求之后等待。后者是本次明确保留的策略。

方案扩展既有 Profile budget：`gpu_vram_reserve_percent` 为 0–100 的整数，
省略或 0 完全保留原固定 `gpu_vram_reserve_mb`。正值时，设备余量为
`ceil64(max(512 MiB, gpu_vram_reserve_mb, 已核定单卡工作负载 × percent / 100))`。
新模板默认绝对下限 512 MiB、比例 5%；新 GPU 运行必须指定正工作负载下限。
旧 Profile、现有运行和共享池不自动降低保护值。此策略是工程起点，不声称 5%
适合所有工作负载。

Host 以同一纯函数计算预览、准入、固定卡检查和运行保护值；核定预算先保留
现有估计、实测 25/15/10% 余量、初始预算及 OOM 下界。数值直接进入现有
ResourceIntent；Oracle 依据原 Profile 和经过验证的工作负载来源复算。
池继续按设备取池下限和请求余量的最大值，仅收取一次，不改 FIFO 或池协议。
初始化预览必须显示实际池下限；仍为 4 GiB 的池不能被 5% 请求绕过。

确实观察到 OOM 后，既有学习机制将下一次同工作负载预算提升至少 25%，
比例余量随之增长；脚本错误、外部占用和保护终止不能伪装成 OOM。专家通过
既有修复、CYCLE_REPORT、SELF_EVOLVE 保留可比较的实测经验，不能自行修改
保留策略或把不完整采样当成全程最大值。本次不新增学习存储、验证协议或并行
事实源：既有 Profile、预注册、池事务、观测和 Oracle 已能覆盖此边界。

验证范围为旧配置兼容、严格参数校验、比例向上取整、实测/OOM 增长、较高池
下限、真实 Host 的预览/提交/保护/收集及 Oracle、FIFO 和隔离 CPU 闭环。
实际 CUDA OOM 率需未来授权的新运行实测；不改当前研究或热升级池。

## 9. 重复释放与 Host 响应延迟（2026-10-10）

当前运行的只读诊断发现：Host STATUS 六次采样中五次等待 9.44–10.75 秒，
进入响应构造后的尾部约 17–19 毫秒。观察器的既有三秒超时因此无法稳定取得
实时专家状态。诊断原始记录位于 `.local/analysis/observer-host-latency-20261010/`。

`SharedGpuHost.reconcile()` 会重放已结束 Process 的释放请求；等待实验启动前
还会再次对账。诊断时每次有 11 个已释放请求，池仍为每次重复释放调用调度器。
只要还有 QUEUED 请求，调度就重新采样 GPU，单次约 0.4 秒。内存隔离重放中，
两次对账产生 22 次采样；仅移除副本中的排队请求后采样降为零。历史 MiMo 运行
使用相同实现，但较长的登记到启动等待集中在仅结束 0–2 个 Process 的阶段。
这些历史时间包含准入和准备，不能当作连续 GPU 队列或 STATUS 延迟记录。

最小修复直接复用池事务内按完整所有者键读取的 `requests.state`：处理 release
时，已是 RELEASED 就返回现有响应，不执行 `_release` 和 `_schedule`。该状态已
持久化，服务重新打开后仍适用；认证、成员授权和请求身份校验仍在返回之前。
首次释放及尚未确认释放的请求继续执行原有流程。真实资源释放后仍调度，排队
所有者通过既有 reserve/status 轮询继续观察外部容量变化，保持 FIFO、公平性、
显存保护、LAUNCHING 恢复和 BOUND 进程存活检查。

失败资产是 Host 主循环的响应时间，边界是幂等清理 RPC 与容量调度之间。
现有稳定请求键、终态、SQLite 事务和普通回归足以修复；不增加新持久化状态、
协议、缓存或独立清理记录。Host 的恢复与对账调用点、监控三秒阈值保持原样。
先验证此修复；只有剩余实测开销需要时，才另行设计 Host 对账合并。

验证覆盖历史重复释放的采样次数、服务重开、首次释放后立即准入、外部容量
恢复后的 reserve/status 推进，以及既有取消、故障恢复、跨所有者隔离和公平性。
隔离 Host/池套接字验证包含排队和慢采样，观察 STATUS 是否满足现有三秒期限，
并独立核对进程、终态和资源残留；合成 GPU 库存不构成实际 CUDA 性能证明。
最终验证结果记入 [qualification](../qualification.md#gpu-release-replay-and-host-responsiveness-2026-10-10)。

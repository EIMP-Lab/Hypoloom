## 2. D1 / P0：每次 init 确认选卡，并确保兼容池可用

### 用户流程

1. 每次 GPU init 刷新设备观察，展示卡号、稳定 UUID、容量、当前占用及本次授权范围。
   上次选择只作为默认建议；非交互入口须给出明确参数。空闲不构成使用授权。
2. 选择本次运行可用的 GPU 子集；与 Profile、安全约束和池成员权限一致。
   池成员集合可以覆盖多个运行，本次选择仍只限制本次运行，不自动改全池权限。
3. 由现有托管脚本查询、创建或复用服务；启动前校验实际 snapshot 的必要能力。
   版本/来源用于解释，是否兼容由现有运行版本要求与服务实际能力决定。
4. 在启动 Grounding 和任何研究 Agent 之前完成校验；直接 CLI 创建入口也执行同一校验。
   `Prepare only` 保留只读/准备语义，真正启动前必须再次检查，预览不预留设备。
5. 最终显示选中的 UUID、池地址、服务处理结果、独立 namespace 和可用/阻断原因。

### 服务生命周期

| 实际状态 | 行为 |
|---|---|
| 无池，无未解决的既有所有权冲突 | 按本次批准的设备与配置托管创建，验证服务能力后启动研究 |
| 兼容池覆盖本次选择 | 复用服务；本次选择可以是成员集合的子集，不必因选卡不同重启 |
| 兼容但当前设备繁忙 | 允许按既有策略等待，明确显示容量状态 |
| 池不兼容或成员范围不满足，仍有依赖运行/请求/进程 | 阻止新的 GPU 运行进入付费阶段，展示依赖和可执行处理方式 |
| 池需要更新，且已证明不再被运行依赖、请求和进程已清理 | 在已授权的托管启动流程中更新/重配服务，验证完成后继续 |
| 服务失联、状态库不可读、归属不明 | 保留未知并阻断自动替换，不能当成空池 |

不能以“GPU 利用率为 0”或“当前池请求为 0”判定池可回收：运行可能正在 Grounding、
CPU 阶段、暂停或等待 API，之后仍要申请 GPU。分别核对既有运行绑定/持久化状态、
实际 Host/进程存活、池请求状态。Host 已退出但运行尚可恢复也不等于依赖终结。

第一版继续使用项目已有标准托管池和 systemd 单元。设备相交的运行复用同一调度器，
不以每个 run 一个新目录的方式创建互不协调的池。发现已有具名池冲突时明确报错；
跨项目或多用户共卡继续使用操作者明确指定的共同服务，不能声称本地扫描建立了全机锁。
第一版不做活跃池的在线成员扩展、自动运行迁移或跨版本数据库迁移。

复用现有池服务锁、SQLite 事务和 systemd 所有权。并发 init 对同一池只能有一个有效
服务；从检查到服务切换期间再次验证依赖，避免另一个 init 刚绑定就被替换。
若现有锁和 Host 绑定路径不能覆盖这个窗口，先收窄为明确拒绝自动替换，不能仅凭一次
扫描宣称安全，也不为方便重建而增加第二套 GPU 所有权账本。

主要位置：`bootstrap.py`、`workflow_host.py` 的创建入口、`shared_gpu_host.py`、
`.claude/skills/autoresearch/scripts/manage_gpu_pool.py`。抽取并复用已有能力检查，
避免 init、预览和提交各自维护能力字符串或判断逻辑。

## 3. D2 / P0：预提交基础设施故障可以交接和恢复

### 故障分类

| 类别 | 所有者与处理 |
|---|---|
| 候选格式、命令、解析器错误 | Agent 在原有预算内修正 |
| 已知容量上界不足 | Agent 按已有资源修订反馈降低真实需求，保留科学约束 |
| 容量暂时占用、正常公平等待 | Host 等待资源，不占用模型调用来轮询 |
| 池不兼容、权限不满足、连接配置失效 | Host 标记资源基础设施阻断，等待处理，避免原样重提 |
| 暂时连接故障 | Host 有界复查同一连接；复查不发起模型调用，超出范围明确等待用户 |
| 未知错误 | 保留原始诊断，不能当成可安全降级的普通容量不足 |

阻断在 Agent 仍存活时即由 Host 的真实工具处理路径记录，绑定原有 run、节点、
Attempt 和池连接。只读预览错误也应出现在 STATUS 中；Agent 自述或伪造错误不能
建立可绕过完成校验的状态。

优先使用现有命令/转换 payload 和 Attempt diagnostics 表达此技术状态；不另建
blocked-job 表、独立状态文件或 GPU 故障账本。Agent 退出后、Host 重启后仍能从
这些既有记录重建阻断原因。该记录不是已接纳的科学候选或实验预注册。

### 结束与后续工作

- 原生 Stop 与 Host postflight 使用同一校验器：有 Host 确认的预提交基础设施阻断时，
  允许按技术中止完成归档和费用结算，不再要求先创建实验；不记为 EXECUTION 科研成功。
- 无阻断证据且没有实验的普通提前结束仍被拒绝。已有已提交实验继续使用原来的
  `waiting_for_experiment_id` 和终态校验，不能借此丢弃在途工作。
- 对受阻节点停止新的提交/模型纠错；同节点改成 CPU 或 `gpus: 0` 不能绕过已记录阻断。
  正常 CPU 任务仍可工作，其他不依赖故障池的节点和已启动实验继续推进。
- 首次实际 Agent 调用和发生的 token/时间/费用照常记账；Host 等待不消耗新的模型
  重试额度，不自动追加任何总预算。
- 扩展现有人工控制入口提供“复查 GPU 资源”。复查同一授权连接的能力、成员和状态；
  失败则保持阻断，成功后通过现有调度恢复原逻辑节点，保留 Git 工作和归档材料。
  不把资源错误伪装成 API 故障，也不复用 API retry 来解除资源或用户暂停状态。
- 只有显式重选执行方案且满足原科学约束时才允许 CPU 方案；不因 GPU 服务异常自动降级。
  已接纳的 CPU grant 不热改为 GPU；它的取消/替换仍必须走原有受授权流程。
- 恢复操作必须尊重操作者停止、技术恢复耗尽、科学终止及剩余预算；一次资源复查不能
  复活不相关的已终结节点。

提交前失败不制造虚假实验、PID、GPU 样本或 CanonicalOutcome。记录阻断、Agent 收尾、
复查、恢复派发之间的崩溃使用既有命令幂等键和事务处理，避免重复启动和重复结算。

主要位置：`workflow_host.py`、`agent_aci.py`、Agent 工具/原生 Hook 路径、
`agent_context.py`、既有人工控制和研究调度路径。

## 4. D3 / P0：摘要请求与局部消息变化保留可靠计量

### 同一个计量器，按结构处理变化

优先级保持：当前请求精确计数 → 同一 relay/模型/协议的完整 usage 加可界定增量 →
明确标注的保守估计与已有有界恢复。

扩展 `counting_material()` 与 `request_capacity()`，覆盖本次实际发生的变化：

1. 既有消息末尾追加纯文本 block，包括摘要指令或可见输出反馈。未变部分必须精确匹配，
   变化部分按新文本字节及结构开销保守计入；不把整段已计量历史重新按字节收费。
2. 已观察的 `tool_use` 上合法缓存注释移动，与现有 text/tool_result 缓存注释等价规则一致；
   只处理已验证的注释字段，tool 名称、参数、ID、顺序必须保持一致。
3. 单个 text block 与同内容字符串的表示等价继续沿用已有规则。

计算结果仍是估计。不得按供应商名称猜 tokenizer、固定按字节除以 4，或因为文本中
包含“summary/compact”就免除容量检查。普通文本与摘要请求执行同一结构规则。
不修改发送给模型的 wire 内容、思考块、签名或历史。

对可支持的纯文本局部替换，若需要纳入第一版，应保留旧请求实测总量并额外计入新的
替换片段，不能用旧片段字节数反向扣 token；超出明确结构范围则不复用该依据。
第一版优先只覆盖本次已复现的追加与表示等价，不开发通用任意历史 diff 计量器。

工具定义、模型、协议、重要配置改变，或出现无法计量的媒体/不透明块时，不沿用旧
usage。完整响应才建立新的计量依据；部分流、拒绝请求不能建立新依据。每次估计直接
对照原始实测请求，不能把上一次估计当成实测继续递推。

保留仍有效的原始计量来源与拒绝原因，不因一次未知历史变化丢失此前观测；但保留记录
不等于允许把它套用到任意后续请求。供应商精确计数不可用时不依赖额外付费探测。

真正超窗或仍无法确认的请求保持本地保护，走已有重建/草稿保留/归档工具观察路径。
原生压缩是一种可用优化，框架恢复不能要求所有 CLI 或供应商都提供它。

主要位置：`context_management.py`、`provider_relay.py`、`agent_sessions.py`、
`provider_observation.py`。不提高默认 context window、删除输出预留或全局关闭容量保护。

## 5. D4 / P1：可观测进度、压缩和故障成本

### 用户能区分的状态

- GPU 配置兼容性、实际授权范围、资源排队、基础设施阻断、用户可用操作。
- Process 的持久化状态、实际存活证据、实际 CPU/GPU grant、已运行时间与墙钟预算。
- 最近日志更新时间、输出增长和已有可识别 trial/epoch 信息。没有训练进度就显示未知，
  CPU 活动不能冒充科研完成百分比，GPU 授权不能冒充 GPU 正在使用。
- CLI 明确报告的压缩开始/完成；relay 本地拒绝、供应商失败；缺少原生事件则显示覆盖未知。
  仅从提示词推断的摘要意图作为诊断推断，不伪装成精确原生事件或控制依据。
- 初始失败、恢复调用及未知结算分别展示；估计字节、当前估计 tokens、最后实测输入、
  累计 token 使用量分开。未知模型价格的 CLI 美元值不能展示为已验证实际费用下界。
- `recovery_exhausted` 明确标注为技术恢复耗尽，保留既有科学验收要求和已有可用操作。

数据复用现有 Attempt、进程注册、日志、provider exchange、原生事件和成本 fold。
有界读取日志尾部；进程观察核对既有归属身份，离线状态不宣称存活。不新增必填
`progress.json`、训练心跳协议或科研事实表，不因日志静默自动取消实验。

运行时指导要求长实验尽量 flush 输出 trial/epoch、耗时及阶段性指标；这些仅是运行
观测，科学结果仍来自原有输出/解析器/接纳路径。先做小规模 LOCAL 筛选，取得运行
耗时与有效性证据再扩大候选/seed/消融规模；具体划分由 Agent 在科学约束内选择。
已冻结的测量与 seed 要求不能被框架自动裁剪，不能拼接失败实验达到 GOAL。

设计/实现 Agent 继续保留已有草稿、实际验证状态和下一步，区分代码修复、CPU 冒烟与
正式实验。不给全部超时一律加时，也不把大量完整训练放在模型调用内等待。

更新 Web/TUI、STATUS、issue report 和既有已授权通知通道；按现有状态变化/去重规则
通知一次关键阻断和恢复，不能每次轮询都发送。教程覆盖中英文 init、GPU 资源、
上下文恢复和故障操作；运行时规则更新 CLAUDE/.claude 的对应来源。

## 6. 最小机制与必要性说明

本次不增加新哈希、冻结声明、校准标记、平行事实库或新的训练进度协议。需要扩展的
验证与技术状态遵循以下边界：

| 扩展 | 具体失败与资产/边界 | 现有手段的能力与不足 | 最小实现、维护与收敛条件 |
|---|---|---|---|
| 启动前池校验 | 旧服务存活却不支持新调度语义；边界是新 Host 与长期运行池 | Git HEAD 不代表进程已加载代码；类型合法的旧 snapshot 仍缺能力；已有 snapshot 校验足以判断，应提前复用 | 抽取一个既有能力校验并用于 init/创建/提交，维护兼容能力映射；删除重复检查，不新增 readiness 文件 |
| 预提交技术阻断与人工复查 | GPU 错误只返回给 Agent，Stop 又强迫提交；故障状态与运行推进边界丢失 | 主键/事务足以承载，但当前记录与控制语义未表示这种阻断；测试不能替代真实运行时交接 | 在既有命令/转换/Attempt 记录中扩展原因及作用范围，复用人工控制；未来若统一技术阻断框架覆盖该语义则合并，不留独立账本 |
| 计量增量匹配 | 局部追加触发全历史字节回退并拦截摘要；边界是已测请求与下一次请求 | Git/事务保证来源与次序，不能推导 token；现有完整 usage 和请求比较足以修复，无需新签名/摘要 | 扩展既有计量函数的结构匹配与诊断；维护确定性正反例，可靠精确计数可用时继续优先采用 |

服务替换是有副作用的运维操作。现有所有权、鉴权、私有数据保护、追加写边界和
不可逆操作约束全部保留；“不新增机制”不能成为绕过这些保护的理由。

## 7. 实施顺序和验收

顺序：复现并保留失败 → D1 → D2 → D3 → D4 → 冻结候选后的整体验证与有限质量评估。
第一轮 D1/D2 先解决 GPU 被绕开；D3 在真实长调用前完成，避免继续支付重复恢复成本。

| 验收场景 | 必须观察到的结果 |
|---|---|
| 新 init 接旧池 | Grounding/付费 Agent 尚未启动即得到明确阻断，无 CPU 降级 |
| 新建、兼容复用、子集选卡、并发 init | 一个有效托管服务，正确的 run namespace/授权范围，不重复启动 |
| 活跃旧运行暂时没有池请求 | 不自动替换其依赖服务；未知依赖也不被当成空闲 |
| GPU 正常但容量暂满 | 仍按原有策略等待和启动，不误判为不兼容 |
| 原生 Agent 遭遇提交前基础设施错误 | 正常结束技术调用并归档；没有伪造实验、重复纠错或 CPU 绕过 |
| 处理故障后复查 | 同一节点在剩余预算内继续，经真实 Process、收集、接纳和下一步闭合 |

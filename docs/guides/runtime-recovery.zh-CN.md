# GPU 启动检查、故障恢复与运行观测

[English](runtime-recovery.md) · 简体中文

已有运行使用创建时固定的运行时；更新仓库不会迁移旧运行，
也不会自动重启其 GPU 服务。

## Web 观察数据的新鲜度

Web 观察器在后台生成下一份数据时，继续显示上次完整结果。
“正在准备观察数据”表示首次读取尚未完成；“已连接 · 正在刷新数据”表示连接正常、
替换数据正在生成；“数据已 … 秒未更新”表示数据的实际年龄，即使 HTTP 请求成功也
不会把旧数据算成刚更新。“数据刷新失败”会保留旧结果并由服务端重试。
“轮询超时”描述的是浏览器请求，不是实验超时，也不能据此判断 Host 已经停止。

浏览器在每次响应后等待 3 秒再轮询，单次请求上限 8 秒，数据超过 15 秒未更新时
显示陈旧提示。隐藏标签页会暂停轮询，切回页面会请求更新。历史记录和所选详情独立
加载，详情慢不会阻塞状态轮询。

Host 忙碌或历史记录较多时，观测可能延迟。收到新的 Host 回复前，活动和 RPM
可能暂不可用。历史数据加载期间，工具次数与证据覆盖率可能显示未知；未知不等于
零活动，也不代表遗漏动作。

更新观察界面后需重新打开监视器；只刷新浏览器不会更新其后端。重新打开同一状态目录、同一运行 ID 的监视器，并使用它给出的新启动
链接。在监视器中按 `q` 离开不会停止 Host 或实验。更新观察器不需要恢复或迁移研究。

## 科学迭代与执行修复

专家卡片分别统计最近已接纳周期中的首次实验、科学迭代和执行修复。并行假设的
首次实验及正常科学迭代不会累加到另一个执行节点的修复次数。专家详情按假设链、
科学迭代列出已记录修复次数、接纳时的修复额度、实验标识及结果或校验代码。

“额度已用完”提示同时依据单节点计数和已记录的可修复失败；实验仍待完成时，
仅达到次数上限不代表失败。执行成功或得到有效科学否定会消除修复告警，修复历史
继续保留。较早迭代和已停止运行的告警标为历史记录。这些计数不能证明科学研究
是否收敛，也不能识别模型能力等失败原因。

批量假设运行使用自身记录的版本、执行节点身份和冻结 Profile 预算；旧单链运行
保留原有周期阈值。批量记录缺失身份字段时显示无法确定，不补成零或猜成旧单链。
独立观察器可只读查看受支持的历史记录，不替换运行包，也不改变资源限制或科学标准。

## 完成回包与最终报告证据

Web 将“已记录的节点最终失败”与持久状态分开显示。展开可查看专家、阶段、
研究链、失败时间、原因及调用详情。这些节点已耗尽自动恢复机会，但其他链
仍可能运行；应结合 Host 存活、调度错误和 Process 状态判断整项任务。
失败记录在运行完成后仍保留。TUI 使用相同的节点计数语义。

新运行会保持有大小上限的日志片段为有效 UTF-8，包括在字节边界截断的进度条；
非文本字节显示为替换字符，原始日志不变。这可以避免日志片段导致分析请求在调用
模型之前失败。

专家应以一个完整 JSON 对象作为最终消息，由原生 Stop 钩子校验；手工调用内部
校验 socket 不代表响应已完成。在完整请求到达前关闭的连接会留下诊断，但不会
禁用后续校验。已通过的输出若变成非法最终消息，先前通过状态会被撤销，并允许在
原有次数和截止时间内纠正。Host 要求实际最终消息与已校验文本完全一致，不会拿
旧候选替代或删除 JSON 外的说明文字。会话身份错误、完整传输帧格式非法及校验器
故障仍会终止校验。这些修改用于新运行，不会重写历史红色错误记录。

本地测量解析器的 `value` 和可选 `baseline` 必须是有限标量数值；分数据集的
详细结果应放在原始工件中。字段非法时错误会指出 `result.value` 或
`result.baseline`；Stop 拒绝原因会保留到下一次修复输入，不再被缺少源文件的
二次解析错误覆盖。VALUE 比较可省略 `baseline`，其他比较仍按声明要求它。

实现阶段在原生 Agent 退出前检查实际源文件和累计 Git 补丁；超限会在同一次调用内
反馈，并沿用配置的 Stop 纠错上限。调用的输出字节预算包括候选和 Base64 编码文件：
已跟踪与未跟踪变更都计入，单独采集的源文件还会出现在补丁中。收到反馈后应缩减
实际文件，并为最终元数据留出空间。退出后才能完整获得的用量、诊断等字段仍由
Host 做最终完整校验。更新仓库不会改变旧运行。

CLI 退出后，新运行只在会话身份、相同结果、当前输出验证和累计用量均一致时，接受后台任务通知
导致的重复完成回包；最后一份累计用量只计入一次。结果发生变化或无法完整计费的额外
回包仍会失败。

最终报告分别获得 Agent 各终态计数、所有未成功 Attempt 的引用，以及耗尽重试或
不可重试的节点。已恢复的失败和人工取消仍属于运行历史。报告从经过验证的发布工件
获取有大小上限的评估摘要及声明的原始文本测量，并列出被省略的文件。缺少 GOAL
验收不代表没有原始测试观测；LOCAL 或失败任务的观测不能经报告变成新的正式结论。

逐 outcome 的 Process 记录与最终响应摘要共用 `process_attempt_details` 和
`process_attempts_by_returncode`。正文和摘要中的显式返回码、终态和 validation_code
都会与这些记录核对。规范结局 `EXECUTION_FAILURE` 可以与 Process `CANCELLED` 并存，
不能据此反推 `raw_execution_failed` 或 rc=70。保留报告不会因新版审计而被就地改写。

若查询计划的覆盖探测成功，但 Grounding 正式检索缺少必要年代分层，Host 会记录
真实的模型调用前检索失败，并在既有重试上限内改写该精确查询，不虚构 Agent 调用、
不复制先前模型费用。Host 重启后从持久 Attempt 重建同一决策。更新仓库不迁移旧运行。


## 初始化 GPU 研究

每次 init 都刷新设备观察并复核精确 UUID 子集。上次选择仅作默认建议，不能自动授权
另一次运行。设备占用反映容量，不代表有权使用。

标准托管池位于项目的 `.local/gpu-pools/shared/control.sock`，并非系统公共池。
设备范围相交的运行复用同一个调度器，各运行仍有独立 namespace 和明确授权的 GPU
子集。兼容池的成员可以多于本次选卡。跨项目或多用户共享须明确配置共同服务。

init 通过 `bootstrap inspect` 区分当前就绪状态与可执行的准备方案。没有池或项目池
缺少必要能力时，只要创建/更新方案可审阅，就可以选择 Start now。Host 仍要求在
Grounding 和研究 Agent 之前确认 `resource_replanning/1`；兼容但繁忙属于容量等待。

`--managed-pool` 将 bootstrap 接入托管服务管理。审阅精确的 `--pool-action`
（create、reuse、restore、upgrade、reconfigure）、全池成员与 reserve。本次运行的
UUID 子集独立于全池成员。兼容池直接复用；升级保留已知服务配置与数据库。停止服务的
原配置无法确认时，必须明确审阅重配参数。普通 `ensure` 仍仅创建/复用，替换需要明确的
审阅动作，不能获得无限重建权限。

维护检查 CREATED 绑定、运行终态、Host/进程所有权及所有未释放池请求。CPU 工作、
Grounding、API 等待、暂停均仍是依赖，不能仅凭无 GPU 请求判定可升级。所有权未知或
数据库不可读会阻止替换。短时目录锁协调维护与新 Host 接纳；已知旧根的 controller 锁
阻止其在维护期间恢复。这些是项目范围检查，不是全机登记。标准托管池要求新状态根
位于所属仓库的 `state/` 下；外部状态根和跨项目共享使用明确配置的外部服务。
外部服务不会被自动替换。

bootstrap 先准备并验证池，再启动 Host、创建运行。失败时保留当前 init 的选择，
提供重新检查、调整选项、Prepare only 或取消，不静默降级为非池/CPU。
Prepare only 不操作池或 Host。池准备成功后，即使 Host 启动失败，健康共享池也会保留。

init 可在准确审阅 `RUN_ID:REVISION` 后，通过原冻结 Host 结束失去 Host 的旧运行。
该入口要求原启动信息可用、无存活所有者且相关池请求全部释放；先记录取消，再恢复
Attempt，只执行收尾及原预算内最终报告。它不恢复研究调度，也不向已停池重复释放
已确认释放的请求。完成后仍需通过原依赖检查。旧版本缺少该能力时保持明确阻塞，
不跨版本迁移；步骤与限制见[初始化指南](initialization.zh-CN.md)。
历史数据库始终保留，不自动迁移，也不承诺旧二进制一定可回滚。
简洁入口与阶段耗时见[初始化指南](initialization.zh-CN.md)。

## 恢复预提交池故障

资源查询或 GPU 提交时，如果 Host 实际观察到池不兼容、不可访问或权限不匹配，
会在现有工作流历史中记录受影响的节点和 Attempt。暂时连接失败会进行一次有界的
只读复查。持续故障会停止该 Agent，归档诊断，按技术失败结算本次调用，不生成实验、
科学结果或成功的执行节点。原生 Stop 根据 Host 确认的状态允许退出，不再强迫提交实验。

受影响节点等待资源恢复，不能通过 CPU 或 `gpus: 0` 绕过故障。无关节点与已提交实验
沿用原调度。候选错误、需要降低真实需求的容量不足、正常容量排队仍按原机制处理。
API 恢复不会清除 GPU 阻断。

修复原绑定服务后，在 Web 操作者恢复链接中点击 **Recheck GPU resources**，
或在 TUI 按 **g**，也可执行：

```bash
hypoloom resource-recheck --state-root /absolute/state/root --run-id RUN_ID
```

Host 复核服务能力、允许的 UUID，并要求故障 Agent 已完成清理；仅解除实际记录的阻断。
原有重试、墙钟和费用预算继续生效。相同请求 ID 可安全重试；若回复未确认，重试原请求，
不要新建另一项操作。Web 沿用受认证和同源限制的操作者恢复链接
（`--allow-provider-control`）；普通监控链接仍只读。复查不改选卡、池绑定或 API。

现有产品事件流提供 `resource_blocked`、`resource_rechecked`。外部通知需在对应
sink 中明确选订；不会自动扩大已有 Telegram/Webhook 订阅范围。

## 理解进度、上下文与费用

STATUS 和 Web 展示实际 CPU/GPU 授权、Host 所持进程的存活、日志字节数及距最近写入
的时间。持久化 `OPEN` 代表尚未结清的所有权，不是心跳。进程活着但日志静默时，
科研进度是未知；不会仅因没有输出就取消。离线视图不能确认操作系统进程存活。
Issue report 保留可获得的派生观察。

训练脚本应及时 flush 阶段、trial/seed、epoch 和耗时信息。在已接纳的方法学允许时，
先做有限 LOCAL 筛选，再进行完整 GOAL 评估。不能为了加速而擅自减少冻结试验次数、
修改解析器或降低目标。

上下文计量在以下有限变化时保留完整 provider 用量：最后一条用户消息追加文本
（后面可有内容不变的 CLI system 消息）、新增文本消息、已知缓存标记或文本表示变化。
模型、工具、协议、签名思考和原消息正文仍严格核对。用原始实测加新增字节保守估算，
不把估算递归当作实测。未知变化继续走保守回退和有界重建。

原生压缩发起和完成边界分别观察；本地上下文拒绝、provider 上下文失败和未完成转发
也分别统计。完成次数为零不代表从未尝试，缺失事件及无法关联的失败仍显示未知。
这些计数不依赖 prompt 中出现“summary”等词。
Web 分别展示转录与开始事件的覆盖范围。`stdout_partial` 表示开始计数仅覆盖日志
尾部，缺失的早期事件仍未知，因此不能直接用开始次数减去全部完成次数。

Web/TUI 用量指标统一使用 token，分别显示已报告、失败/恢复调用、预留与未知
用量。缺少模型定价不作为运行告警。内部保留历史金额证据及已配置的金额预算，
这些观察不代表已经验证成本收益。

Host 仅在实际接纳 Agent Attempt 后计算本轮派发次数。执行控制者等待自己已提交
的实验时，不消耗该次数，其他就绪任务可继续推进。授权 GPU 空闲本身不代表调度
故障，应分别检查可运行请求、实际资源分配和 Process 存活。

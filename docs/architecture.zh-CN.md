# 架构概览

[English](architecture.md) · 简体中文

Hypoloom 通过常驻 Workflow Host 协调研究。专家提出假设和实验，Host 调度
获准工作并记录结果，独立 Oracle 校验已记录证据与执行一致性。

## 从目标到证据

1. **配置**：六文件 Profile 定义目标、专家、方法、语言、通知和安全限制。
   初始化先审阅目标仓库、数据、模型与资源权限，再启动新运行。
2. **目标澄清**：通过文献和人工答复澄清目标。选择共同验收时，Grounding 提供
   实验共用的评估器和有效性检查。
3. **研究**：专家阅读论文、提出假设、设计实现、请求实验、分析结果并修订方向。
   辩论、选出的 Leader 和技能演化支持协作。
4. **执行**：Host 校验提交的设计，在获准环境中启动有界 Process。候选代码、
   原始输出和测量 parser 均有明确输入及归属。
5. **评估**：获准测量与对应假设、实验关联，科研判断和目标评估依据这些证据；
   最终报告说明结果、限制和未完成工作。

各阶段的使用方法见[研究工作流](guides/research-workflow.zh-CN.md)与
[阅读和提案](guides/reading-and-proposals.zh-CN.md)。

## 组件职责

| 组件 | 职责 |
| --- | --- |
| Workflow Host | 持久状态、请求准入、调度、收集与结果发布 |
| 研究 Agent | 科研提案、候选代码与限定范围内的工具调用 |
| 实验 Process | 在获准限制内完成真实 CPU/GPU 计算 |
| GPU 池 | 参与运行的资源承诺与容量分配 |
| Oracle | 独立验证身份、结果、证据和生命周期一致性 |
| Web 与终端观察界面 | 只读状态投影及明确的操作员动作入口 |
| 操作员 | 目标、凭据、预算、设备授权、人工答复与停止 |

Agent 使用私有工作区和受限工具。研究期间，原始目标仓库与获准数据根目录只读。
文件和命令权限不代表可以编辑框架、扩大资源授权或直接写运行数据库。
获准状态始终由 Host 写入。

## 状态与结果

运行状态根目录保存 SQLite 记录、产物和运行时包。Command 与 Attempt 标识工作
由谁请求、由谁执行；获准科研事实关联目标、假设、实验、证据和评估。日志用于排障，
获准记录及其产物用于确定运行实际产生了什么。

`ACTIVE` 记录本身不能证明 Host 存活，需要另看当前 Host 观测。
`COMPLETED` 也不直接代表科学目标达成，需要检查目标结论、获准测量及最终报告。
不同 LOCAL 结果不能拼成一个未实际通过的共同 GOAL 候选。

## 资源与预算

CPU/GPU 实验使用启动前审阅的环境和路径。GPU 需要明确的设备授权；共享池记录
资源分配，工作负载的实测显存可以用于后续申请。其他用户的 GPU 活动不属于池内
承诺，因此仍需实时容量和压力检查。详见[GPU 资源](guides/gpu-resource-planning.zh-CN.md)。

运行、专家、Agent 和 Process 的限制分别约束不同范围。更长的实验超时不会延长
Agent 截止时间。已报告用量、在途预留和未知费用分别保留，估算不等于上游账单。

## 观察与恢复

Web 和终端读取相同的持久科研记录。人工答复、供应商切换及 End run 均是明确命令；
关闭观察界面不会停止研究。End run 请求取消并等待所属工作关闭。操作方式见
[使用指南](../USAGE.zh-CN.md)与 [API 恢复](guides/provider-recovery.zh-CN.md)。

每个运行保留原有运行时包和获准配置，更新仓库不会升级已有运行，也不支持跨版本迁移。
不要直接修改 SQLite 修复运行；遵循[运行恢复](guides/runtime-recovery.zh-CN.md)
和备份说明。
